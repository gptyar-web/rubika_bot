# سرویس JavaScript پنل Rubika Control Pro

صفحه عمومی با HTML، CSS و JavaScript در GitHub Pages اجرا می‌شود. این پوشه سرویس اختیاری **JavaScript** مبتنی بر Supabase Edge Functions (Deno) و پایگاه داده PostgreSQL را فراهم می‌کند؛ پایتون یا سرور پایتون لازم نیست. GitHub Pages خودش تابع سرور، نگهداری امن کلید سرویس، دریافت Webhook و کار زمان‌بندی‌شده اجرا نمی‌کند.

کد حاضر روی Supabase شما منتشر نشده است. Endpoint قبلی پنل و جدول‌های `rubika_panel_bots` و `rubika_panel_groups` در طول توسعه تغییر نکرده‌اند. نسخه ۳ از جدول‌های مستقل `rubika_panel_v3_*` استفاده می‌کند، ولی قرارداد `health/login/list/save/delete` را حفظ کرده است. نصب و انتقال داده باید ابتدا روی یک پروژه آزمایشی انجام شود؛ منتشرکردن تابع هم‌نام در پروژه قبلی، تابع موجود را جایگزین می‌کند.

## آنچه واقعاً اجرا می‌شود

- هر درخواست احراز‌شده توکن همان تب را با `getMe` بررسی می‌کند. توکن، کلید سرویس و URL توکن‌دار در پایگاه داده یا لاگ برنامه نوشته نمی‌شوند.
- تنظیمات گروه و کانال، پیش‌نویس، قالب، برنامه خودکارسازی، برنامه زمان‌بندی، تیکت، دفترچه کاربران، تخلفات و رضایت‌ها در دیتابیس ذخیره می‌شوند.
- تاریخچه عملیات را فقط سرور می‌سازد و از API قابل حذف یا ویرایش نیست.
- ارسال متن، پاسخ، نظرسنجی، مکان، مخاطب، استیکر با شناسه موجود، فایل با `file_id` موجود، فوروارد، ویرایش متن، حذف پیام و دریافت اطلاعات گفتگو فقط از Adapter مجاز انجام می‌شوند. موفقیت به پاسخ واقعی `status: OK` روبیکا وابسته است.
- دریافت `getUpdates` با درخواست کاربر یا Worker خصوصی انجام می‌شود. فراداده رویدادها با Hash یکتا ثبت می‌شوند؛ متن کامل پیام در جدول رویدادها ذخیره نمی‌شود.
- ثبت UUID عملیات از ارسال دوباره درخواست مشابه جلوگیری می‌کند. پاسخ مبهم شبکه دوباره به‌صورت خودکار ارسال نمی‌شود.

**ذخیره تنظیمات قدیمی، اجرای خودکار آنها نیست.** از نسخه ۳٫۱ موتور و اجرای درخواستی اضافه شده‌اند؛ مدیریت به `moderation_enabled` و `moderation_authorized` و `active`، و پاسخگویی نیز به `active` و `automation_enabled` و `automation_authorized` نیاز دارد. برنامه فقط با تأیید صریح اجرا می‌شود. اجرای دائمی به Worker خصوصی نیاز دارد. Webhook، RBAC و احراز هویت دومرحله‌ای هنوز تکمیل نشده‌اند. فهرست قابلیت‌های `health` این محدودیت‌ها را مشخص می‌کند. ثبت نقش در دفترچه کاربران، نقش امنیتی ایجاد نمی‌کند. دریافت اطلاعات اعضا، اخراج، محدودسازی، مسدودسازی و سنجاق پیام در Adapter وجود ندارند.

## مرجع API و حدود اعتبارسنجی

مرجع رسمی `https://rubika.ir/botapi` در محیط توسعه پاسخ HTTP 403 داد؛ بنابراین آزمون زنده با توکن واقعی انجام نشده است. قرارداد متدهای مجاز از مخزن درخواستی `AliRn76/rubika-bot` با Commit زیر بررسی شد:

`203da2e585f03d6b2cef96cbd7a68b471e010db7`

فایل‌های مرجع: `rubika_bot/requests.py`، `docs/en/docs/methods.md` و مدل‌های داده. تنها Base URL موجود در این مرجع مجاز است: `https://messengerg2b1.iranlms.ir/v3`. کد غیرفعال‌کردن TLS موجود در Upload مرجع کپی نشده است؛ هیچ Upload چندبخشی یا تشخیص نوع فایل از حدس پیاده‌سازی نشده است. Keypad فعلاً فقط دکمه `Simple` را می‌پذیرد. ارسال رسانه نیاز به `file_id` معتبر از روش مجاز موجود دارد و Caption رسانه پشتیبانی نمی‌شود.

## راه‌اندازی آزمایشی

پیش‌نیازها: Node.js نسخه ۲۰ یا بالاتر برای تست‌ها، Supabase CLI، Docker برای اجرای محلی Supabase، و یک پروژه Supabase آزمایشی برای انتشار. فایل‌های تابع وابستگی خارجی JavaScript ندارند.

۱. در ریشه مخزن تست‌های بدون نیاز به توکن را اجرا کنید:

```bash
npm --prefix server test
# اختیاری: PostgreSQL موقت با Docker؛ پس از تست حذف می‌شود.
npm --prefix server run test:sql
```

۲. در محیط توسعه محلی Supabase را آغاز و Migration را اعمال کنید:

```bash
supabase start --workdir server
supabase db reset --workdir server
```

`db reset` تنها برای پایگاه داده **محلی آزمایشی** است؛ روی اطلاعات کاربر اجرا نشود. برای پروژه‌ای با داده موجود، Migration افزایشی را با `db push` روی پروژه صحیح اعمال کنید.

۳. تنظیمات خصوصی را خارج از پوشه عمومی سایت قرار دهید. فایل [`.env.example`](.env.example) فقط نام‌ها و نمونه‌های غیرواقعی دارد. برای اجرای محلی، آدرس/کلید محلی را از خروجی خصوصی CLI بگیرید؛ آنها را به چت یا Git نفرستید. برای Production، `SUPABASE_URL` و `SUPABASE_SERVICE_ROLE_KEY` در Edge Function توسط Supabase تزریق می‌شوند و نباید دوباره با دستور `secrets set` تنظیم شوند. فایل خصوصی Production فقط شامل `SCOPE_SALT`، `ALLOWED_ORIGINS`، `RUBIKA_API_BASE` و `ALLOW_LOCALHOST=false` باشد.

`SCOPE_SALT` باید تصادفی، پایدار و حداقل ۳۲ نویسه باشد. شناسه ربات تأییدشده با HMAC-SHA256 این راز به Scope داده تبدیل می‌شود؛ تعویض توکن معتبر همان ربات داده‌ها را حفظ می‌کند، ولی تغییر Salt آنها را در Scope جدید قرار می‌دهد. Salt را با روشی امن پشتیبان‌گیری کنید. مقدار Origin مسیر `/rubika_bot/` ندارد: `https://mozdbaranarshiya.github.io`. در توسعه محلی فقط با `ALLOW_LOCALHOST=true`، Originهای HTTP روی `localhost` و `127.0.0.1` پذیرفته می‌شوند.

```bash
supabase functions serve rubika-panel --workdir server --env-file /tmp/rubika-panel-local.env
```

پاسخ عمومی بدون توکن:

```bash
curl --fail-with-body http://127.0.0.1:54321/functions/v1/rubika-panel \
  -H 'Content-Type: application/json' --data '{"action":"health"}'
```

۴. برای انتشار ابتدا پروژه آزمایشی را Link کنید و تنظیمات خصوصی را از فایل خارج مخزن بخوانید:

```bash
supabase link --project-ref YOUR_STAGING_PROJECT_REF --workdir server
supabase db push --workdir server
supabase secrets set --env-file /tmp/rubika-panel-production.env --workdir server
supabase functions deploy rubika-panel --workdir server --no-verify-jwt
```

توکن روبیکا جای JWT کاربر Supabase بررسی می‌شود، به همین دلیل `verify_jwt=false` در `config.toml` وجود دارد. کلید `service_role` فقط داخل تابع است؛ هر دوازده جدول RLS دارند و دسترسی مستقیم نقش‌های `anon` و `authenticated` و اجرای عمومی RPCها لغو شده است.

۵. آدرس تابع جدید را در تنظیمات پنل وارد کنید. `health.version` باید `3.1` باشد؛ سپس با توکن معتبر واقعی ورود، ذخیره و بازیابی تنظیمات و ارسال یک پیام آزمایشی به مقصد دارای مجوز را بررسی کنید. `configured` در پاسخ `health` فقط حضور متغیرها را بررسی می‌کند؛ تضمین دسترسی زنده دیتابیس یا روبیکا نیست. تا پیش از این آزمون‌ها، اتصال Production «آزمایش‌شده» محسوب نمی‌شود.

## انتقال از پنل قبلی

از Endpoint قبلی تنظیمات را در پنل دریافت و نسخه پشتیبان JSON تهیه کنید. سپس Endpoint پروژه آزمایشی نسخه ۳ را انتخاب و رکوردها را با `save` یا گزینه بازیابی پنل وارد کنید. هنگام مقایسه شناسه گروه، عنوان و تنظیمات را بررسی کنید. Migration حاضر جدول‌ها یا سیاست‌های قبلی را دست‌کاری نمی‌کند و با ساختار نامعلوم آنها Import خودکار انجام نمی‌دهد. هر Bot Scope باید با توکن همان ربات احراز شود؛ Scope یا کلیدها را دستی در Frontend قرار ندهید.

## نگهداری و امنیت عملیاتی

محدودیت نرخ در دیتابیس اتمی است: مجموع درخواست‌های احراز‌شده ۱۲۰ در دقیقه، هر ربات ۶۰ در دقیقه و عملیات پیام هر ربات ۲۰ در دقیقه. CORS فقط Origin مجاز مرورگر را محدود می‌کند؛ مرز اصلی امنیت، اعتبارسنجی `getMe` در هر درخواست است. Cookie یا نشست قابل ارسال خودکار مرورگر استفاده نمی‌شود.

Rubika توکن را طبق قرارداد API در مسیر HTTPS دریافت می‌کند. تنظیمات Redaction لاگ‌های Proxy و زیرساخت را برای این مسیر بررسی کنید؛ خود تابع پیام خام خطا، URL توکن‌دار یا Stack trace را چاپ نمی‌کند. Payload خام درخواست‌های Panel را در سرویس‌های Log ثبت نکنید. تنظیمات زمان‌بندی و قالب‌ها اجازه ذخیره فیلدهای Credential یا متن شامل توکن فعال را نمی‌دهند. کلیدها تنها در Environment Secrets تنظیم شوند.

پس از Timeout ارسال، ابتدا مقصد را بررسی کنید؛ UUID همان عملیات را برای پرس‌وجوی دوباره نگه دارید. `unknown` یا `pending` عمداً دوباره ارسال نمی‌شود. برای عملیات جدید پس از بررسی نتیجه، UUID جدید بسازید. لاگ‌ها و رکوردهای عملیات برای اطمینان از عدم ارسال تکراری حفظ می‌شوند؛ پاک‌سازی یا دوره نگهداری آنها باید با نیاز واقعی شما تنظیم شود. ابزار SQL Integration هیچ پروژه Supabase واقعی را تغییر نمی‌دهد.

قرارداد کامل درخواست‌ها در [API.md](API.md) آمده است.

## راه‌اندازی موتور نسخه ۳٫۱

هر سه migration پوشه `supabase/migrations` به‌ترتیب لازم‌اند؛ نسخه جدید جدول‌های خصوصی runtime، نشست، job، lease و collections تکمیلی را اضافه می‌کند و داده‌های نسخه قبلی را حذف نمی‌کند. اجرای `db push` فقط روی پروژه صحیح و با پشتیبان انجام شود؛ reset پایگاه داده کاربر مجاز نیست. راهنمای [Worker و Docker](runtime/README.md) و قرارداد [API](API.md) مراحل را توضیح می‌دهند.

قواعد به رویدادهای پیش از زمان فعال‌سازی جدید اعمال نمی‌شوند. پردازش فعلی فقط `NewMessage` مستند است؛ انواع رویداد دیگر اجرا نمی‌شوند. دکمه‌های پیشرفته یا رسانه‌های بدون نوع قطعی حدس زده نمی‌شوند. منوها و فرم‌ها فقط پاسخ `sendMessage` تولید می‌کنند و مجوز دلخواه ایجاد نمی‌کنند.

TTL فرم حداکثر ۱۵ دقیقه است؛ پاسخ منقضی بازگردانده نمی‌شود. پاک‌سازی فیزیکی با Worker فعال یا دسترسی بعدی انجام می‌شود و هنگام توقف کامل زیرساخت فوری نیست. نتیجه نامشخص، pending و ثبت ناقص عمداً برای ارسال خودکار مجدد قابل استفاده نیستند. برای برنامه‌ای که سابقه اجرا دارد نسخه تازه با شناسه تازه و تأیید مجدد بسازید.
